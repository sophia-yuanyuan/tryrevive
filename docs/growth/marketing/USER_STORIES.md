# 用户故事

状态：场景设计稿，非真实用户证言

以下人物和经历均为虚构，且全部聚焦在校大学生，用于说明目标场景、产品流程和验收信号。未经真实用户授权，不得将这些内容改写成客户评价或使用效果证明。

所有故事当前研究状态均为 `未验证场景`。真实会话、反证和授权状态统一记录在 [`../../research/RESEARCH_LOG.md`](../../research/RESEARCH_LOG.md)，不得在本文件中制造验证结论。

## 故事一：搁置三周的课程项目

### 背景

小林是一名计算机专业大三学生，同时面对课程大作业和竞赛项目。三周前他完成了课程项目的登录界面，但此后被考试和其他作业打断。重新打开仓库时，他只记得“登录还有问题”，不知道问题具体在哪里。

### 用户故事

> 作为一名重新回到课程代码库的大学生，我希望快速恢复上次的目标、最后产出和阻碍，从而不用先花一晚上重新理解整个项目。

### TryRevive 流程

1. 小林记录项目目标、最近一次可见产出和当前阻碍。
2. TryRevive 把模糊的“修好登录”缩小为“在 25 分钟内复现一次登录失败，并把错误信息保存到项目记录”。
3. 小林完成复现，保存日志文件名作为证据。
4. Return Plan 记录下一次从该错误信息开始排查。

### 可观察成功信号

- 生成的动作只有一个交付物；
- 动作具有时间盒和完成标准；
- 用户留下了可供下一次继续的证据；
- 再次进入时不需要重新描述全部背景。

## 故事二：截止日期临近的作品集

### 背景

阿宁正在准备作品集。她已经有截图、项目说明和个人经历，但文件散落在不同文件夹。每次想到“完善作品集”，都会因为任务太大而转去做别的事。

### 用户故事

> 作为一名准备作品集的学生，我希望把“完善作品集”缩小成今天能完成的一项产出，从而在有限时间里留下真实进展。

### TryRevive 流程

1. 阿宁选择“作品集”项目并填写当前材料与截止日期。
2. 产品生成一个微动作：“用 20 分钟为 TryRevive 项目写出 80–120 字的问题、行动和结果说明。”
3. 她将完成的段落文件名作为证据保存。
4. 下一次动作被安排为选择一张可公开截图，而不是继续扩展整份计划。

### 可观察成功信号

- 用户完成一段可直接复用的内容；
- 产品没有生成完整作品集 backlog；
- 公开照片、经历或效果数据仍需在发布前单独确认。

## 故事三：AI 给了很多方案，但竞赛项目没有推进

### 背景

周然是一名正在参加创新竞赛的大学生。他已经和多个 AI 工具讨论过产品方向，聊天记录里有功能列表、架构建议和展示思路，但团队仓库一周没有新产出。

### 用户故事

> 作为一名高频使用 AI 的大学生，我希望把已有讨论压缩成一个可验收动作，从而让 AI 帮助完成竞赛交付，而不是继续生成更多建议。

### TryRevive 流程

1. 周然把已有目标和最近产出整理为上下文快照。
2. TryRevive 只生成一个 Action Contract，包括执行者、所需能力、时间盒和完成标准。
3. 如果需要 Agent 写文件或提交代码，产品明确提示该动作需要授权。
4. 完成后保存文件或 commit 链接，并安排下一次回流。

### 可观察成功信号

- 输出是一个动作，而不是新一轮路线图；
- 外部写操作没有在未授权时发生；
- 完成记录区分用户自述和可验证证据。

## 故事四：课程调研时被推荐流带走

### 背景

小夏是一名传播学专业学生，正在完成课程调研，需要去公众号和视频平台找两个案例。她经常打开平台后开始浏览推荐内容，半小时后忘记原本的问题。

### 用户故事

> 作为一名需要在内容平台完成课程调研的大学生，我希望带着明确问题进入平台，并在限定时间后回到项目，从而减少无目的浏览。

### TryRevive 流程

1. 小夏先写下本次检索问题和所需证据。
2. 她通过关键词直达或应用入口进入平台，并设置浏览时间。
3. 回流提示要求她保存链接、标题或摘录，然后返回当前动作。
4. 如果平台访问受限，她可以手动粘贴公开正文；产品不绕过登录或验证码。

### 可观察成功信号

- 浏览行为与一个具体项目动作绑定；
- 用户带回了可引用的公开来源；
- 产品没有突破平台访问限制。

## 故事五：毕业设计做过一次，但几天后又从头开始

### 背景

陈默是一名正在做毕业设计的大四学生。他已经为项目做过多次短冲刺，但每次只记得“好像推进了一些”。下次进入时，他仍要重新判断哪些内容已经完成。

### 用户故事

> 作为一名断续推进毕业设计的大学生，我希望每次结束时保存证据和下一次入口，从而让未来的自己能从真实进展继续。

### TryRevive 流程

1. 动作完成后，陈默填写产出位置或链接。
2. 系统保存当前上下文、完成证据和 Return Plan。
3. 到达计划时间后，产品从上次证据生成恢复入口。
4. 周复盘展示已完成动作，而不是只展示计划数量。

### 可观察成功信号

- 恢复入口引用上次的真实产出；
- 用户能判断“做了什么”和“接下来做什么”；
- 成功不以聊天次数或生成计划数量衡量。

## 故事六：下一步不对，学生选择“帮我问清楚”

### 背景

若琪的竞赛项目停了十天。系统最初建议她继续完善 Demo 页面，但她真正的阻碍是团队尚未确定要解决的用户问题。继续切小页面任务只会制造看似完成的进度。

### 用户故事

> 作为一名觉得系统建议偏离真正问题的学生，我希望能够指出建议为什么不对，并只回答少量关键问题，从而得到更符合项目现状的下一步。

### TryRevive 流程

1. 若琪点击“换一个”，选择“背景理解错”。
2. 产品提供可跳过的“帮我问清楚”，一次只问一个决策问题，最多 3 问。
3. 她确认当前真正需要的是获得 3 名目标学生对问题描述的反馈，而不是继续做页面。
4. 新的下一小步是写出一段 80 字的问题描述并发给一名已约好的同学。

### 可观察成功信号

- 卡点诊断只在建议被拒绝后出现；
- 用户可以随时跳过并直接要下一步；
- 新动作回到一个可见产出，不生成另一份长报告；
- 记录建议被拒绝的原因，而不把拒绝当成用户失败。

## 故事七：最有帮助的结果是暂停一个项目

### 背景

明轩同时开了课程项目、比赛和个人应用三个坑。个人应用已经两个月没有明确用户或截止节点，但他因为“都开始了”一直不愿停止。

### 用户故事

> 作为一名同时推进太多项目的学生，我希望判断哪个项目值得继续、哪个应该暂停，从而把有限时间留给真正重要的交付。

### TryRevive 流程

1. 明轩恢复个人应用的最近现场和当前节点。
2. 产品让他在继续、缩小、求助、暂停和放弃中做选择。
3. 他选择暂停，并记录重新评估条件，而不是获得一个为了完成率而制造的小任务。
4. 下次首页不再用提醒制造内疚，只保留手动恢复入口。

### 可观察成功信号

- 暂停或放弃与继续同样可达；
- 产品不把所有项目停滞都解释为动作太大；
- 用户事后认为该取舍释放了时间或减少了无意义推进；
- 暂停项目不计入“复活成功”来美化指标。

## 可继续验证的问题

- 哪类用户最频繁遇到“上下文断裂”而不是单纯拖延？
- 多长的恢复流程能提供足够信息，又不会造成新的启动摩擦？
- 用户更愿意保存哪类证据：文字、文件名、链接还是 commit？
- 哪种回流方式最能让用户从证据继续，而不是产生打扰？
- 注意力守护应该在哪些场景出现，才不会抢走项目复活的主定位？
- 哪些情况下条件式卡点诊断帮助澄清，哪些情况下只是增加负担？
- 暂停或放弃一个项目，是否比生成更小动作更有价值？
