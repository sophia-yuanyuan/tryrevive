# 学生 MVP 体验规格

状态：P0 交互基线，待可用性测试

更新日期：2026-08-02

## 1. 体验目标

第一次打开 TryRevive 的学生，应该在三分钟内完成一件事：

> 从一个真实停滞项目中，得到并认可一个今天能完成、完成后能看见变化的下一小步。

产品必须降低重新进入项目的心理和信息成本，不增加仪式、测试或行政感。

## 2. 生命周期不是页面顺序

```text
Revive
恢复现场 → 判断是否值得继续 → 可选卡点诊断 → 确认下一小步

Loop
执行 → 留下进度 → 安排回流 → 从上次成果继续

Learn（仅内部）
观察失败模式 → 提出改动 → 固定案例评测 → 小流量验证 → 人工批准或回滚
```

因此，“Loop 是第二个环节”在生命周期层面成立。下一小步确认前属于 Revive；记录 `action_started` 后进入首轮 Loop。它不是首页后的第二张表单。

## 3. 首次体验总览

| 阶段 | 用户要解决的决策 | 页面唯一主动作 | 退出或分流 |
|---|---|---|---|
| 欢迎 | 这是否适合我的停滞项目 | 复活我的项目 | 看如何工作 |
| 恢复现场 | 上次做到哪里、为什么停 | 回答当前问题 | 返回、稍后补充 |
| 项目判断 | 还值得继续吗 | 选择处理方式 | 暂停、放弃 |
| 卡点诊断 | 哪个判断还不清楚 | 接受或修改本题答案 | 跳过、直接给一步 |
| 下一小步 | 现在唯一值得做什么 | 现在开始 | 缩小、替换、编辑、暂停 |
| 执行 | 怎样完成这个产出 | 完成这一步 | 暂停、还是太大 |
| 留下进度 | 这次真实产生了什么 | 保存本次成果 | 稍后补充 |
| 回流 | 下次从哪里、何时继续 | 保存并结束 | 生成下一小步 |

## 4. 页面规格

### 4.1 欢迎页

首屏文案：

- 标题：`让搁置的大学项目重新动起来`
- 副标题：`找回上次做到哪里，完成今天最关键的一步；下次从真实进度继续。`
- 主按钮：`复活我的项目`
- 信任说明：`无需注册即可试用 · 数据默认保存在本机`

可展示课程大作业、竞赛 Demo、作品集、毕业设计四个简短场景。不得先要求登录、看强制叙事、做人格测试、选择主题或设置桌宠。

### 4.2 恢复现场

逐题展示，不超过 5 个核心问题：

1. 这是什么项目？
2. 最近一次实际完成了什么？
3. 最接近的截止节点是什么？
4. 当前最大的阻力是什么？
5. 今天能投入多少时间？

要求：

- 每次只问一个问题；
- 显示明确进度；
- 允许返回修改；
- 提供示例，但不能替用户虚构答案；
- 对“没有最近成果”提供正常选项，不产生羞辱感。

### 4.3 项目判断

五个选项应平等呈现：

- 继续；
- 缩小目标；
- 需要帮助；
- 暂停；
- 放弃。

产品不能默认所有项目都值得复活。选择“需要帮助”时，应区分缺技能、缺反馈、缺伙伴、缺权限或缺材料。

### 4.4 可选卡点诊断

用户入口使用 `帮我问清楚`，不要展示 `GrillMe`。

触发方式：

- 用户主动点击；
- 核心信息不足，规则无法产生可信建议；
- 用户拒绝、替换或二次缩小建议；
- 回流后再次卡在同一位置。

交互规则：

- 最多 3 问；
- 一次只问一个决策问题；
- 每题提供推荐答案及原因；
- 用户可接受、修改或跳过；
- 始终可点击 `直接给我一个下一步`；
- 不把跳过视为失败。

示例问题：

1. `这次要先决定：这个项目还值得继续吗？`
2. `十分钟后，别人能看到哪一个具体变化？`
3. `当前建议不对，主要因为：背景理解错 / 太大 / 没价值 / 缺技能 / 缺依赖 / 今天没时间？`

P0 使用确定性问题树。原始 `grill-me` 适合创始人做 PRD 压力测试，不直接作为学生端语气。

### 4.5 下一小步

页面只突出一张行动卡：

- 现在做什么；
- 预计 5–20 分钟；
- 什么状态算完成；
- 为什么建议这一步。

可用操作：

- `现在开始`；
- `再缩小一点`；
- `换一个`；
- `自己修改`；
- `先暂停`。

选择后四项时记录原因，但不得强制输入长文本。

### 4.6 执行

只显示当前动作、完成标准、计时器和工作入口。允许暂停、完成和反馈 `还是太大`。冥想、桌宠、MBTI、励志弹窗、应用 Dock 和无关推荐不得阻挡核心动作。

### 4.7 留下进度

用户文案使用 `留下进度` 或 `本次成果`，并说明：

> 记录成果是为了让下次不用重新回忆，不是为了审查你。

支持文字、链接、文件名或 commit 等成果位置。系统可以验证来源和时间关联，但不能因此声称成果质量已被验证。

使用中性问题让用户回答：`和开始这一步之前相比，这份成果是否让项目产生了实质推进？`，允许“是 / 否 / 不确定”和补充原因，不能用庆祝文案诱导选择“是”。

指标要求同时存在一条绑定当前动作的成果记录，并把 `claimed / observed / source_verified` 分开；来源可核对不等于成果价值已被客观验证。

### 4.8 完成与回流

展示：

- 这次实际完成了什么；
- 下次从哪里继续；
- 下次继续时间。

主按钮：`保存并结束`

次按钮：`生成下一小步`

不使用夸张庆祝动画，也不以动作数量制造成就感。

### 4.9 再次进入

十秒内呈现：

1. 上次成果；
2. 上次决定的下一入口；
3. 截止节点是否变化；
4. `继续上次` 主按钮。

只有当项目目标、阻力或外部状态已经明显变化时，才重新进入恢复或卡点诊断。

## 5. 失败与边界状态

| 状态 | 产品响应 |
|---|---|
| 没有最近成果 | 接受事实，改问“你最后记得的现场是什么” |
| 项目不值得继续 | 帮助记录暂停或放弃理由，不制造失败感 |
| 缺技能或反馈 | 给出求助型下一步，不继续把动作切小 |
| 建议连续被拒绝 | 进入最多 3 问的卡点诊断 |
| 时间不足 5 分钟 | 保存现场并安排合适回流，不生成无意义动作 |
| 离线 | 核心本地流程继续可用 |
| 数据损坏 | 显示恢复、导入或重新开始选项，不静默覆盖 |
| 提醒被拒绝 | 保留手动回流入口，不重复索要权限 |

## 6. 响应式与可访问性

- 优先支持 390×844，并验证 360×800、768×1024、1440×900；
- 触控区域至少 44×44px；
- 文字与控件达到 WCAG AA 对比度；
- 提供可见键盘焦点；
- 不只依赖颜色表达状态；
- 支持 `prefers-reduced-motion`；
- 处理软键盘遮挡、200% 缩放、长中文和屏幕阅读器标签。

## 7. 事件记录需求

获得明确同意后，最少记录：

- 是否在 3 分钟内获得可接受动作；
- 建议策略版本；
- 是否触发卡点诊断、问题数和是否中途退出；
- 接受、缩小、替换、编辑或暂停；
- 拒绝原因；
- 是否留下成果；
- 用户是否认定为实质推进；
- 7/30 天是否再次推进；
- 回流时是否需要重新解释。

事件只用于产品学习，具体口径见 [`METRICS_AND_EXPERIMENTS.md`](METRICS_AND_EXPERIMENTS.md)。

## 8. 当前实现映射

现有 `brief / running / evidence / completed / paused` 状态可以继续作为底层实现：确认下一小步前为 Revive，进入 `running` 或记录 `action_started` 后为首轮 Loop。`sessions.length` 只用于显示已经完成的轮次，不用于判断是否已经进入 Loop。P0 不需要为了引入这些概念重写状态机。
