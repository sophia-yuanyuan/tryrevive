# TryRevive 学生 MVP 产品需求文档

状态：P0 产品基线，待真实学生验证

更新日期：2026-08-02

## 1. 这份文档负责什么

本文件只定义学生 MVP 要解决的问题、用户体验、范围和验收标准。技术数据结构、迁移、连接器和部署方案分别记录在 V3 技术实现规格与 ADR 中，不在这里决定产品优先级。

90 天获取 1,000 名学生是增长目标，不是当前成绩，也不能替代产品价值验证。

## 2. 核心用户

首发只服务一类人：

> 有一个已经停滞至少 7 天的课程、竞赛、作品集、科研或毕业设计项目，并且近期存在提交、答辩、展示、比赛或申请节点的高校在读学生。

创业者、独立开发者和职场知识工作者可以参与访谈、提供反馈或帮助转介绍，但不是前三个月的主动获客对象，也不计入 1,000 名学生目标。

## 3. 要验证的问题

学生无法继续一个项目，可能由不同原因造成，MVP 不能默认全部属于“上下文丢失”：

- 忘了上次做到哪里；
- 下一步太大或完成标准不清楚；
- 项目本身已经不重要；
- 缺少技能、反馈、合作伙伴或必要依赖；
- 知道下一步，但不愿承担枯燥、困难或失败；
- 同时开的项目太多，应该缩小、暂停或放弃其中一部分。

核心假设是：

> 如果 TryRevive 能在三分钟内帮助学生找回现场、判断项目是否值得继续，并给出一个学生认可的最小但有意义的下一步，学生会更可能在 7 天内留下真实成果，并在 30 天内再次推进。

这个假设目前尚未被足够的真实用户数据证明。

## 4. 用户需要完成的任务

当一个重要项目停滞后，学生希望：

1. 不必重新翻完所有群聊、文档、代码和聊天记录；
2. 判断这个项目应该继续、缩小、求助、暂停还是放弃；
3. 知道今天唯一值得完成的产出是什么；
4. 知道什么状态算完成；
5. 留下真实进度，让未来的自己不用再次从零理解。

## 5. 产品承诺

> 找回上次做到哪里，完成今天最关键的一步，下次从真实进度继续。

最早的价值时刻不是“创建了项目”或“生成了计划”，而是用户在三分钟内看到并认可一个具体下一步。

## 6. 用户生命周期

### Revive：第一次复活

`恢复现场 → 判断是否值得继续 → 必要时问清卡点 → 确认一个下一小步`

### Loop：持续推进

`执行 → 留下进度 → 安排回流 → 从上次成果继续`

Loop 是第一次复活后的第二阶段，但不是一个单独页面。对学生端使用“下一轮”“从上次继续”等自然语言，不展示 `Loop`、`RSI`、`Action Contract` 等内部概念。

### Learn：内部产品学习

团队每周从获得同意的去标识、假名化事件和访谈中寻找重复失败模式，提出一个小改动，经过隔离评测和人工批准后发布。Learn 不属于用户功能，也不能让系统直接修改线上规则、提示词或代码。

## 7. P0 用户流程

1. **进入**：无需注册即可开始，首屏只说明服务对象、结果和隐私边界。
2. **恢复现场**：逐题回答不超过 5 个核心问题，包括项目、最近成果、截止节点、主要阻力和今天可用时间。
3. **项目判断**：选择继续、缩小目标、需要帮助、暂停或放弃。
4. **可选卡点诊断**：只在信息不足、建议被拒绝或用户主动选择时追加最多 3 个问题；可以随时跳过。
5. **下一小步**：给出一个 5–20 分钟的初始动作，包含产出、完成标准和推荐理由；任何动作不得超过 45 分钟。
6. **纠正建议**：用户可以接受、再缩小、换一个、自己修改或暂停，并说明拒绝原因。
7. **执行**：页面只保留当前动作、完成标准、计时和工作入口。
8. **留下进度**：保存文字、链接、文件名或其他成果位置，并让用户判断它是否构成实质推进。
9. **安排回流**：选择 3–7 天内的继续时间，明确下次从哪里开始。
10. **再次进入**：十秒内看到上次成果和下一入口，不要求重述全部背景。

## 8. 条件式“卡点诊断”

该能力借鉴 `grill-me` 的逐题澄清方式，但不会把“relentless interview”原样施加给已经对项目有压力的学生。

触发条件包括：

- 用户无法指出最近一次真实成果；
- 目标只有过程描述，没有可见结果；
- 当前阻力选择“不清楚”；
- 用户点击“换一个”或“自己修改”；
- 用户第二次表示动作仍然太大；
- 回流后再次卡在同一位置。

每题必须：

- 只解决一个决策；
- 给出一个推荐答案及一句理由；
- 允许接受、修改、跳过；
- 显示 `1/3` 等进度；
- 提供“直接给我一个下一步”的退出入口。

P0 先使用确定性问题树，不依赖 LLM。

## 9. 功能范围

### 必须有

- 无注册的首次体验；
- 恢复现场与项目判断；
- 条件式卡点诊断；
- 单一下一小步及完成标准；
- 接受、缩小、替换、编辑、暂停；
- 文字、链接或文件名形式的进度记录；
- 3–7 天回流与从上次成果继续；
- 本地保存和主动导出；
- 获得同意后才记录去标识、假名化产品事件。

### 暂不做

- Team、企业权限、审计和管理员功能；
- 自动选择或执行 Agent/Skill；
- 多模型网关的用户功能；
- 多工具 OAuth 和自动写入外部系统；
- 付费套餐和商业化承诺；
- 自动修改线上提示词、规则或代码；
- 注意力诊断、心理治疗或医疗功能；
- 为了增加完成率而生成没有实质价值的小任务。

## 10. 用户可见语言

| 内部术语 | 学生端使用 |
|---|---|
| ProjectState | 上次项目现场 |
| Context Snapshot | 最近进展 |
| Action Contract | 下一小步 |
| Completion Evidence | 留下进度 / 本次成果 |
| Return Plan | 下次从这里继续 |
| Resume Packet | 上次做到这里 |
| Grill / Grilling | 帮我问清楚 / 卡点诊断 |
| Loop | 下一轮 / 从上次继续 |

内部可以保留现有数据字段，但不得要求学生理解这些术语。

## 11. 验收标准

### 体验验收

- 首次用户无需注册即可开始；
- 从点击主 CTA 到看到可接受下一步不超过 3 分钟；
- 每个页面只有一个主要动作；
- 核心问题不超过 5 个，条件问题不超过 3 个；
- 用户可以选择暂停或放弃，而不是被迫复活所有项目；
- 手机端单手可以完成主流程；
- 再次进入时可以从上次成果继续。

### 价值验收

- 学生能解释为什么当前动作值得做；
- 7 天内产生一个学生本人认定为实质推进的成果；
- 30 天内再次推进同一项目；
- 回流时不需要重新解释全部项目背景。

具体计算口径和实验门槛见 [`METRICS_AND_EXPERIMENTS.md`](METRICS_AND_EXPERIMENTS.md)。

## 12. 发布门槛与停止条件

在扩大获客前，先完成至少 5–10 个真实停滞项目的完整观察。若多数学生不能在三分钟内获得可接受动作，或者 7 天内没有产生被本人认可的实质成果，停止增加平台、Agent 和自动化功能，回到问题与体验验证。

若用户主要需要的是项目取舍、技能帮助或外部反馈，应调整恢复问题与分流，不把所有失败都解释为“动作还不够小”。
